# 開發 EMV Part II

2018 年 12 月 17 日

在第一部分中，我們已經建立了幾個基礎觀念：EMV 交易不是單一步驟，而是分階段進行；晶片與讀卡機之間的大量互動由 Kernel 處理；交易結果會以 TLV（Tag-Length-Value）形式回傳；而且交易過程中通常會出現兩次與 Tag 9F26 相關的 cryptogram。

本篇重點是把這些概念轉成「實作時要怎麼讀資料、怎麼判斷、怎麼送授權」。

## 線上授權與 Complete 階段

一般流程中，你會先在前段取得第一批交易資料（含第一個 cryptogram），將後端處理器需要的 TLV 一併送出做線上授權。這段工作需要由你的支付應用程式負責，因為讀卡機與 SDK 不會替你直接完成 gateway 授權請求。

授權端回應後，常見會帶回 Tag 89、8A、91，以及可選的 71 或 72。接著把這些資料交給交易完成階段（Complete Transaction）所需的 API。完成後，回呼資料中通常會包含第二個 cryptogram（同樣在 Tag 9F26）。

## 如何判讀 cryptogram 類型

Tag 9F26 本身是加密結果，不能只看內容就知道其型態。通常要搭配 Tag 9F27（Cryptogram Information Data）來判斷。

在實務上，開發者最常遇到的狀態可簡化為：

- ARQC：建議連線到線上主機做授權。
- TC：卡片端建議可通過。
- AAC：卡片端建議拒絕或離線失敗情境。

要特別注意：這些值多半是「卡片建議」，不等於最終清算結論。最終結果仍由線上授權方（issuer / processor）決定。某些模式（例如 Quick Chip）在特定時機下看到 AAC 也不代表交易一定無法清算，需依整體授權流程判讀。

## TLV 擷取的常見誤區

常見誤解是：以為所有需要的 Tag 都會在交易最後一次回來。實際上，EMV 是分階段回傳資料，若你在某個階段沒先擷取，後面可能就拿不到同一批關鍵值。

因此建議做法是：

- 在 Start / Authenticate / Complete 每一階段都做 TLV 蒐集。
- 依你的處理器規範整理出「每階段必抓 Tag 清單」。
- 以結構化方式保存（例如 phase + tag map），避免除錯時資料遺漏。

## 哪些 Tag 可能會加密

若裝置已注入金鑰並啟用加密，敏感欄位（例如 Track 或 PAN 相關 Tag）通常會以加密形式輸出。生產環境下，應讓資料安全地直通後端處理器，不建議在前端或應用層自行解密敏感資料。

## 小結

第二部分最關鍵的收穫有三點：

- 交易分階段，資料也分階段回傳。
- cryptogram 類型要搭配 9F27 解讀，不可只看 9F26。
- 卡片回應是建議，最終交易結果仍由線上授權端決策。

把這三件事釐清後，EMV 串接會更接近可維運、可除錯、可擴充的工程狀態。
